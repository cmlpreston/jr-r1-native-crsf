## 14 November: ABS candidate — Forward/Brake only, not flashed

After the live-endpoint upload, user requested ABS and specifically rejected
pulsing reverse. Explained that physical brake/reverse input and unsigned RPM
cannot identify ESC direction. User chose "Require Forward/Brake mode for ABS".
No ESC setting or receiver firmware has been changed for ABS.

Implemented `brake_abs.h`: default Off, activation 30%, release depth 30%, 5 Hz,
200 ms delay; fixed 50% strong/reduced duty. Adjustable point/depth 10–90%, rate
2–10 Hz and delay 0–1000 ms. Pure runtime in ControlEngine follows mixed shaped,
trimmed, limited and slewed throttle output, but activates only on the physical
brake side and matching output direction. Release cannot cross signal centre
into forward, including shifted neutral and reversed throttle. CUT/reset/input
fault/configuration fault and final stale-output arbitration remain authoritative.
There is no wheel-lock sensing, steering mixing or switch activation yet.

ABS eligibility requires an actually accepted session/sequence-matched ESC Read
or verified Write of Surpass parameter 7 with raw value 1 (Fwd/brake). It is
saved per model in a strict checksummed/versioned 12-byte record. This is cached
configuration evidence, not live mode feedback: external card/other-transmitter
changes require another read. A fresh Program request or run-mode write disables
ABS and clears eligibility before proceeding. ABS must be re-enabled explicitly
following mode verification. Reversible/unknown modes cannot enable ABS. Invalid
ABS storage inhibits normal arming; deliberately editing an ABS setting retries
storage. No automatic ESC run-mode changes.

UI: Tune -> Brake -> second page -> ABS braking. ESC mode row opens the existing
programmer. Shared settings rows show mode first, then On/Off, activation, brake
release, frequency and delay. Header ABS marker means enabled, not necessarily
pulsing. Edits request CUT and normal neutral re-arm. Mode records and settings
are isolated by model. Original R1 manual pp33–34 confirms pulse depth/pattern/
delay and optional steering mixing/switch operation; current numeric controls
are a deliberately smaller first implementation rather than copied patterns.

## Surpass ESC protocol reference recovered — 5 November 2026

User supplied the missing dedicated repository:
https://github.com/cmlpreston/surpass-esc-programming-protocol
Detailed notes: `docs/protocol.md` in that repository. Consult it rather than
reconstructing the protocol from the inert R1 ESC preview.

Measured bus: one data wire plus ground, idle-high, half-duplex, 8-N-1 LSB-first;
ESC ~800 bit/s and card ~820 bit/s, both decoded at 800. Startup ESC `1B FF`,
card `1C FF`; read `1C <id> 00` -> `1B <value>`; write `1B <id> <value>` ->
`1B 0A`. IDs/values are zero-based, with non-numeric printed choice ordering.
Write persistence confirmed after power cycle. `0A` success meaning remains
inferred pending negative test. No checksum apparent in captures. Fifteen
parameter mappings 00..0E documented; decoder and capture tests in that repo.

Electrical idle voltage/open-drain behaviour not yet fully characterized. Notes
propose level-protected RX plus MOSFET pull-low TX (never actively drive DATA
high), separate GPIOs, and passive capture/read emulation before writes. Do not
connect the ESC data wire directly to receiver GPIO based on UART mapping alone.
Permanent-connection feasibility still needs programming-entry/re-entry and
normal throttle coexistence verified; startup capture alone does not prove this.

proven requirement. Stock ELRS supports remapping and a secondary serial interface

R1 configuration -> existing routed CRSF parameter request/reply mechanism
